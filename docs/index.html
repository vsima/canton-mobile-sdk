The native wallet stack for Canton.

Swift and Kotlin SDKs for building self-custody wallets on the Canton Network. Keys are created inside the Secure Enclave or Android StrongBox and can never leave the device. Transactions are verified on the phone before the hardware signs. Payments, the token standard, and dApp connections work out of the box, so you build the product, not the plumbing.

SwiftSecure Enclave
import CantonWalletKit

// Created in the Secure Enclave, never exportable
let driver = try SecureEnclaveSigningDriver()

// A party only this device can act for
let party = try await ExternalPartyClient(client: client)
    .allocate(driver: driver, synchronizerId: sync,
              partyHint: "alice")

// Prepare on the node → re-verify the hash on device
// → sign in hardware → execute
let submission = InteractiveSubmissionClient(client: client)
let tx = try await submission.prepare(
    commands: [pay], actAs: party.partyId,
    synchronizerId: sync)
try await submission.signAndExecute(
    prepared: tx, driver: driver, partyId: party.partyId,
    keyFingerprint: party.publicKeyFingerprint)
KotlinStrongBox / TEE
import io.github.vsima.canton.wallet.*

// Created in StrongBox (TEE fallback), never exportable
val driver = AndroidKeystoreSigningDriver
    .generate(alias = "wallet")

// A party only this device can act for
val party = ExternalPartyClient(channel)
    .allocate(driver, synchronizerId, partyHint = "alice")

// Prepare on the node → re-verify the hash on device
// → sign in hardware → execute
val submission = InteractiveSubmissionClient(channel)
val tx = submission.prepare(
    listOf(pay), party.partyId, synchronizerId)
submission.signAndExecute(
    tx, driver, party.partyId, party.publicKeyFingerprint)

One SDK family, two first-class languages. Every release covers Swift and Kotlin together and passes the same test vectors, so your iOS and Android apps always behave the same.

Why native

The official SDKs are TypeScript. Phones are not.

The ecosystem's @canton-network SDKs are excellent for Node and the browser. A mobile wallet needs what only the platform can give: hardware key storage, biometric approval, and connections that survive real-world mobile networks. This SDK is that layer, in the languages your team already ships in.

Keys live in silicon

Signing drivers for the Secure Enclave and the Android Keystore (StrongBox first, TEE fallback), software drivers for tests, and a DelegatingSigningDriver hook for custody providers.

Your users truly hold their own assets: no server ever sees a key or can move funds on its own, and every transaction is verified on the device by default before the hardware signs it.

The whole wallet surface

Balances, a payment inbox, and transfers with memos on the CIP-0056 token standard. Instant receiving through preapprovals, including cancel. Full transfer history with counterparties and net amounts.

Plus fee previews, name lookups, test funds, traffic purchase, gap-free state sync, and typed errors with retry hints. The feature set of a production wallet, ready before you write your first screen.

dApps connect natively

Give dApps the standard way in: wallet sign-in, message signing, and one-tap payments over WalletConnect, LAN, or in-process transports, with every request gated by approval screens you control.

Both sides of the CIP-0103 protocol ship in the box, tested against the published spec, so your wallet speaks the same language as the rest of the Canton ecosystem.

Verified where it counts

Hardware claims, tested on hardware.

Apps inherit the claim "hardware-backed" from their SDK. This one proves it at every security tier, on physical devices.

Secure Enclave Apple's dedicated security coprocessor iPhone, on device VERIFIED
StrongBox Dedicated secure element, Android Samsung Galaxy Z Flip5, on device VERIFIED
Hardware TEE Android Keystore trusted execution environment OnePlus Open, on device VERIFIED
Secure Enclave, macOS Apple silicon Macs, the real enclave Every CI run VERIFIED

Beyond the key stores, both SDKs run their full integration suites against a live Canton network: onboarding, signing, token transfers, and preapprovals, end to end. Shared test vectors pin the security-critical behavior, like transaction hashing and message signing, so Swift and Kotlin can never quietly drift apart.

Ecosystem compatibility

Works with Canton's official stack. Proven live.

Compatibility is demonstrated, not promised. The reference storefront is built on Digital Asset's official @canton-network TypeScript SDKs, and it signs users in and takes one-tap WalletConnect payments from a wallet built on this SDK, end to end, on both platforms. Build on this SDK and you plug into the same ecosystem every Canton dApp targets.

Install

One dependency. Take the layer you need.

Standard tooling, no exotic setup: add one dependency from Maven Central or Swift Package Manager, start at the layer that matches your app, and each layer includes everything beneath it.

Swift Package Manager
dependencies: [
  .package(
    url: "https://github.com/vsima/canton-mobile-sdk.git",
    from: "0.6.0"),
]
// then import CantonWalletKit, CantonDappKit, …
Gradle
dependencies {
    implementation(
        "io.github.vsima.canton:canton-wallet-sdk:0.6.0")
    // + canton-wallet-android for StrongBox / TEE keys
}

The dApp app

The least a dApp needs: a minimal client built from the dApp module alone, with no path to keys or the ledger. That boundary keeps third-party dApps out of your users' wallets, and CI enforces it on every run.

Agents

The agent asks. The human approves. The secure element signs.

Give your users an assistant that can pay, without ever handing it a key. canton-agent-mcp connects any MCP agent to a wallet built on this SDK, and the agent can only ask: every request lands as an approval sheet on the phone, is verified on the device, and is signed in the Secure Enclave or StrongBox. Shown here as it happened, live on both sides at once.

agent session canton-agent-mcp · MCP over stdio

Nothing to trust but the phone. The agent never holds a key or a session token: it names the request, the wallet prepares it on its own participant, re-verifies the transaction hash on device, and StrongBox signs only what the human approved. The QR is real; scan it for the source.
